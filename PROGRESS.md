**Phase 17b — Two-way maintenance task reconciler with user-work preservation:** The one-way `MaintenanceTaskMigrator` from Phase 47 only ever ADDED tasks when a quiz answer unlocked a new subtype, which left "Descale tankless heater" and other stale templates lying around when a user later confirmed they had a tank gas water heater. The new `MaintenanceTaskReconciler` is the inverse: it converges the task list for a system to the templates that match the currently-confirmed subtype, soft-deleting rows that no longer apply AND adding any newly-applicable ones in one idempotent pass. Replaces and deletes the old `MaintenanceTaskMigrator.swift`.

**Schema:** New migration `20260425_maintenance_task_archive.sql` adds `is_archived BOOLEAN NOT NULL DEFAULT false`, `archived_at TIMESTAMPTZ`, `archived_reason TEXT` columns plus `idx_maintenance_tasks_active` partial index on `(household_id, is_archived) WHERE is_archived = false`. `MaintenanceTaskDBRow` and `MaintenanceTaskUpdate` (Swift) gained matching `isArchived`/`archivedAt`/`archivedReason` fields with `is_archived = false` filter on every default fetch via a new `includeArchived: Bool = false` parameter on `fetchMaintenanceTasks`, `fetchVehicleMaintenanceTasks`, and `fetchAllMaintenanceTasks`. New `DatabaseService.archiveMaintenanceTask(id:reason:)` does the soft-delete via inline `ArchivePayload` struct so `MaintenanceTaskUpdate`'s nil-omitting Codable doesn't accidentally drop the field. The legacy hard-delete `deleteMaintenanceTask(id:)` is left in place for explicit user deletes.

**User-work preservation:** A task is preserved (never archived by the reconciler) when ANY of these are true: `lastCompletedDate != nil` (user marked complete at least once), `assignedToUserId != nil` (user reassigned it), `notes != nil && !notes.isEmpty`, OR title doesn't match a known template title for the category (i.e. user-added custom). New `MaintenanceTemplates.knownTemplateTitles(forCategory:)` and `allTemplates(forCategory:)` helpers expose the title universe for the reconciler to use as the "is template-managed?" gate; they're separate from `templates(for:activeSubtypes:)` which is still subtype-filtered for the initial setup path.

**Reconciler behavior:** `MaintenanceTaskReconciler.reconcile(propertyId:householdId:systemId:systemCategory:confirmedSubtype:fuelType:flags:)` (1) computes the correct templates via `MaintenanceTemplates.essentialTemplates` for the active subtype set, (2) fetches existing active tasks for the property, narrows to this system via systemId match → templateId prefix → known-title fallback, (3) creates any newly-applicable templates that aren't already present (delegating to `createMaintenanceTask` dedup), (4) for any existing task whose title isn't in the correct set AND that's still recognised as template-managed AND that the user hasn't touched, calls `archiveMaintenanceTask` with reason `subtype_mismatch:{category}:{subtype}`. `reconcileAll(propertyId:householdId:)` walks every system on the property and runs the per-system pass, then runs an orphan pass for category names that don't have a matching system row. Returns a `ReconciliationResult { added, removed, preserved }` that's mergeable across calls.

**Quiz wiring:** `HouseQuizAnswerMapper.apply(question:answer:)` now returns `MaintenanceTaskReconciler.ReconciliationResult` (was `Void`). The four pre-existing migrator call sites — q1 roof, q3 heating fuel, q8 water heater, q11 lawn — now call `MaintenanceTaskReconciler.reconcile` instead of `MaintenanceTaskMigrator.addSubtypeTasks`. Three new sites added: q6 water source (Well System), q7 sewer/septic (Septic System), q12 pool (Pool/Spa with `saltwater`/`chlorine` subtype). `HouseQuizViewModel` exposes `@Published var reconciliationTotals: ReconciliationResult = .empty` and merges each apply result into it, then runs a final `MaintenanceTaskReconciler.reconcileAll` pass after the user answers the last question (gated on a `finalReconciliationDidRun` flag so subsequent persists are no-ops). ## Phase 52: Bulletproof Quiz State Persistence and Resume (Phase 19)

Tom answered several quiz questions, hit X → "Save and exit", returned later, and his answers were gone — back to Q1. Root cause was a stack of four bugs at the persistence edges: the X dialog only called `dismiss()` (no save at all), `saveForLater()` fire-and-forgot its persist, `firstUnresolvedIndex()` ignored `savedForLater` so deferred questions resurfaced immediately on resume, and `persistState`'s catch silently swallowed errors so failed saves vanished into the Xcode console where TestFlight users will never see them. Single bundled commit, no new features.

**The fix (one commit):**
- `HouseQuizViewModel`: new `@Published savedAndReady` and `saveErrorMessage`. New `saveAndExit()` async function awaits a throwing `persistStateThrowing()` and only flips `savedAndReady = true` on success — on failure it sets the error message and leaves in-memory answers untouched so the user can retry without losing anything. Added `persistStateThrowing()` (the throwing variant) and rewrote `persistState()` as a wrapper that catches and logs to `quizPersistFailed` for the per-answer auto-save path.
- `firstUnresolvedIndex()` now skips `savedForLater` AND `skipped` (was only skipped). Save-for-later now actually defers the question instead of bouncing the user right back to it on resume.
- `init` kicks off a defensive `refreshPropertyStateFromDB()` background Task that re-fetches the property and adopts its quiz state if the DB has more answers than the in-memory copy. Covers stale dashboard caches and the multi-device case (Scenario E).
- `HouseQuizView`: X button confirmation dialog's "Save and exit" button now `await viewModel.saveAndExit()` then checks `savedAndReady` before dismissing. On failure the dismiss never happens — instead an inline red error banner pinned to the top of the ZStack appears with the failure message and a Retry button that re-runs `saveAndExit()`. On success a brief "Your place is saved." toast renders for ~900ms before dismissing.
- The milestone "Save for later" button on the section-complete card was also just calling `dismiss()` — now it goes through `saveAndExit()` and only dismisses on success.
- Added `quizSavedAndExited`, `quizSaveAndExitFailed`, `quizPersistFailed` analytics events.

**Why this matters:** Tom's exact symptom was "I saved and my answers were gone." The dialog message used to literally say "Your place is saved" while the button only called `dismiss()`. Worse, even the per-answer auto-save could silently fail with no UI surface, so a flaky network would lose work without the user ever knowing. After Phase 19 the X button is the only path that needs to succeed for state to persist, and if it fails the user sees the error and can retry — and crucially their in-memory answers stay put through the retry loop.

When the user edits a home system's subtype or category via `EditSystemSheet` (e.g. HVAC "not_sure" → "boiler_radiant", or Water Heater nil → "tank"), the existing orphan-confirmation dialog was removing inappropriate template tasks correctly, but it wasn't adding any of the templates that became newly applicable under the new subtype. Users upgrading from Not Sure to a real type saw the same task list and wondered whether the app had actually done anything. Phase 19d adds the missing "add" half while keeping the orphan dialog's keep/delete choices authoritative.

**New `ReconcileMode` enum on `MaintenanceTaskReconciler`.** Three values: `.full` (the existing behavior — add newly-applicable templates AND soft-delete orphans), `.addOnly` (only insert templates that became newly applicable, never delete), and `.removeOnly` (only soft-delete orphans, never add — included for symmetry). The new `mode: ReconcileMode = .full` parameter on `reconcile(propertyId:householdId:systemId:systemCategory:confirmedSubtype:fuelType:flags:mode:)` defaults to `.full` so every existing caller (`HouseQuizAnswerMapper`'s eight per-question reconcile sites, `HouseQuizViewModel.runFinalReconciliation`, `AppState.reconcileAllPropertiesOnce`, and the two internal `reconcileAll` loops) keeps working unchanged. The implementation gates the template-insert block on `mode != .removeOnly` and the task-archive block on `mode != .addOnly`.

**`EditSystemSheet.commitSave` wires the reconciler in.** After `db.updateHomeSystem` returns the new row and after any orphan deletions from the confirmation dialog complete, the sheet runs:
```swift
await MaintenanceTaskReconciler.reconcile(
    propertyId: updated.propertyId,
    householdId: updated.householdId,
    systemId: updated.id,
    systemCategory: updated.category,
    confirmedSubtype: updated.subtype,
    fuelType: updated.catalogFuelType,
    mode: .addOnly
)
```
Gated on `updated.subtype != system.subtype || updated.category != system.category` so no-op saves (user changed only a note or manufacturer) skip the reconcile entirely. `.addOnly` mode guarantees the reconciler never touches existing tasks, so the user's explicit "Keep tasks" choice from the orphan dialog is preserved — the cooling tune-up they said keep still gets kept, and "Bleed radiators" / "Annual boiler service" land alongside it.

**Confirmation toast.** `@State var addedTaskCount` on `EditSystemSheet` drives a bottom overlay that renders a small cream card with a green checkmark and "Added N new maintenance task(s)" copy, styled the same as Phase 19's "Your place is saved." toast. The sheet delays dismissal by ~1.2 seconds (`Task.sleep(nanoseconds: 1_200_000_000)`) when `addedCount > 0` so the toast is actually visible, then dismisses normally. When nothing was added the dismissal is instant. The toast posts `.maintenanceTaskChanged` so the parent `SystemDetailView` / `MaintenanceScheduleView` refresh their task lists once the sheet goes away.

**Verification (traced):** (a) Q3 "Oil" → Q3b "Not sure" produces an HVAC system named "HVAC System (unconfirmed)" with three tasks (replace air filters + cooling and heating tune-ups), matching the Phase 19c scenario. (b) Editing that system to "boiler_radiant" triggers the orphan dialog for "Professional HVAC tune-up (cooling)" (since `boiler_radiant` drops `has_ac` from active subtypes); after confirming deletion, the `.addOnly` reconcile runs and inserts "Bleed radiators" and "Annual boiler service" (both require `boiler`, which `boiler_radiant` now emits). Toast reads "Added 2 new maintenance tasks". (c) Same flow but choosing "Keep tasks" on the orphan dialog: cooling tune-up stays because the orphan delete was skipped, AND the boiler tasks still land because `.addOnly` runs independently. Toast reads the same. (d) Editing a Water Heater from unset to "tank" runs the same path — "Flush water heater", "Test T&P relief valve", "Inspect anode rod" all become newly applicable via the `tank` flag and land via `.addOnly`.

**Known gap (out of scope):** The `SystemSubtypePicker` HVAC option list doesn't include the Phase 19b-added `boiler_with_central_ac` / `boiler_with_window_ac` subtypes or a "Not sure" entry, so users editing from the Phase 19c "unconfirmed" state see whatever raw value SwiftUI falls back to when the current selection doesn't match any tag. The picker still works — the user can pick any of the six existing values and save — but a future polish pass should add the new Phase 19b types to the picker for consistency with q3b.
