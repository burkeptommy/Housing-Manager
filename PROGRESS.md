## Phase 56 Section 5 Patch: Duplicate Detection Refinements (Build 93 — 2026-04-16)

Two bugs surfaced after Section 5 shipped: (1) the "Landscaping" routine was matching every landscaping-category task from Blue Fox as a "duplicate" even though Blue Fox legitimately handles multiple distinct landscaping sub-services under one category umbrella, and (2) the `MaintenanceDuplicateSheet` dismissed after each resolution, forcing the user back to the banner to tap through every subsequent duplicate instead of chaining through the queue.

**Fix 1 — Title similarity gate:** Vendor + category is necessary but not sufficient. Added `DuplicateDetector.titleSimilarity(_:_:)` with Jaccard overlap on tokenized content words, plus a `similarityThreshold` of 0.25. Real work was in the home-maintenance stop-word tuning: the patch's starting list (`schedule`, `check`, `annual`, `seasonal`, etc.) gets most cases but misses the frequent fillers — `system`, `visit`, `appointment`, `home`, `house`, `property`, `professional`, `biweekly`, `triweekly`, `daily`, `yearly`, `test`. The detector now does **word-form normalization BEFORE stop-word removal** so plural / `-ing` / `-ed` forms collapse to their stems (`cleaning` → `clean` → stopped; `gutters` → `gutter` → kept as content; `sprayed` → `spray` → kept; `inspected` → `inspect` → stopped). The normalization is guarded by minimum-length so tiny words don't collapse to empty strings (`"ing"` suffix only strips when `count > 5`, `"ed"` when `> 4`, `"s"` when `> 3`). Trade-specific content words are intentionally kept: `boiler`, `furnace`, `pool`, `gutter`, `tree`, `chimney`, `mosquito`, `tick`, `smoke`, `detector`, `softener`, `heater`, `septic`, `well`, `pump`, `drain`, `sweep`, `cleanup`, `tune`. An empty-token fallback uses substring match on the raw lowercased strings so routines labeled entirely in stop words (e.g. just `"Cleaning"`) still find matches on the task side. Gate applies in `scan()` Pass 1 + Pass 2 and in both `preventionCheck(...)` / `preventionCheckForTask(...)` creation-time checks via a new optional `newTitle:` parameter (empty-string default preserves legacy call sites). `RoutineEditSheet` passes `label`, `AddMaintenanceTaskSheet` passes `title`, and both add `.onChange(of:)` hooks on the title field so the warning re-evaluates as the user edits.

**Fix 2 — Auto-advance through the duplicate queue:** The prior implementation had `MaintenanceDuplicateSheet.resolve()` call `dismiss()` after `onResolve`, and then the parent tried to set `reviewingMatch = next`. SwiftUI's `.sheet(item:)` races the two events — the dismiss animation is in flight when the re-present fires, so the user bounces back to the list and has to tap the banner for each subsequent match. Fix: the sheet no longer owns its lifecycle. Removed `@Environment(\.dismiss)` and the `dismiss()` call entirely. Added `currentIndex: Int`, `totalCount: Int`, and `onCancel: () -> Void` params. Replaced the trailing Cancel with a Done button that calls `onCancel()`. Moved "Review duplicate" from the scroll content into a principal toolbar item that also renders "`N of M`" progress when the queue has 2+ items. The parent's `handleDuplicateResolution` now always writes `reviewingMatch`: to the next match in the queue (SwiftUI swaps sheet content in place, no dismiss/re-present animation) or to `nil` (queue empty → dismisses). Same pattern as Apple Photos' Review Duplicates pagination.

**Files touched:** `Haven/Shared/Utilities/DuplicateDetector.swift` (+120 lines for similarity helpers + gates), `Haven/Features/Property/Views/MaintenanceDuplicateSheet.swift` (rewritten for parent-driven lifecycle + progress toolbar), `Haven/Features/Property/Views/MaintenanceScheduleView.swift` (sheet wiring + handler auto-advance), `Haven/Features/Property/Views/RoutineEditSheet.swift` (pass `newTitle: label`, add `.onChange(of: label)`), `Haven/Features/Property/Views/AddMaintenanceTaskSheet.swift` (pass `newTitle: title`, add `.onChange(of: title)`).

- Blue Fox "Landscaping" vs "Winterize irrigation system" → 0.0 → no longer false-positives
- Blue Fox "Landscaping" vs "Landscaping spring cleanup" → 0.5 → surfaces (legitimately same service)

## Phase 52: Bulletproof Quiz State Persistence and Resume (Phase 19)

Tom answered several quiz questions, hit X → "Save and exit", returned later, and his answers were gone — back to Q1. Root cause was a stack of four bugs at the persistence edges: the X dialog only called `dismiss()` (no save at all), `saveForLater()` fire-and-forgot its persist, `firstUnresolvedIndex()` ignored `savedForLater` so deferred questions resurfaced immediately on resume, and `persistState`'s catch silently swallowed errors so failed saves vanished into the Xcode console where TestFlight users will never see them. Single bundled commit, no new features.

**The fix (one commit):**
- `HouseQuizViewModel`: new `@Published savedAndReady` and `saveErrorMessage`. New `saveAndExit()` async function awaits a throwing `persistStateThrowing()` and only flips `savedAndReady = true` on success — on failure it sets the error message and leaves in-memory answers untouched so the user can retry without losing anything. Added `persistStateThrowing()` (the throwing variant) and rewrote `persistState()` as a wrapper that catches and logs to `quizPersistFailed` for the per-answer auto-save path.
- `firstUnresolvedIndex()` now skips `savedForLater` AND `skipped` (was only skipped). Save-for-later now actually defers the question instead of bouncing the user right back to it on resume.
- `init` kicks off a defensive `refreshPropertyStateFromDB()` background Task that re-fetches the property and adopts its quiz state if the DB has more answers than the in-memory copy. Covers stale dashboard caches and the multi-device case (Scenario E).
- `HouseQuizView`: X button confirmation dialog's "Save and exit" button now `await viewModel.saveAndExit()` then checks `savedAndReady` before dismissing. On failure the dismiss never happens — instead an inline red error banner pinned to the top of the ZStack appears with the failure message and a Retry button that re-runs `saveAndExit()`. On success a brief "Your place is saved." toast renders for ~900ms before dismissing.
- The milestone "Save for later" button on the section-complete card was also just calling `dismiss()` — now it goes through `saveAndExit()` and only dismisses on success.
- Added `quizSavedAndExited`, `quizSaveAndExitFailed`, `quizPersistFailed` analytics events.

**Why this matters:** Tom's exact symptom was "I saved and my answers were gone." The dialog message used to literally say "Your place is saved" while the button only called `dismiss()`. Worse, even the per-answer auto-save could silently fail with no UI surface, so a flaky network would lose work without the user ever knowing. After Phase 19 the X button is the only path that needs to succeed for state to persist, and if it fails the user sees the error and can retry — and crucially their in-memory answers stay put through the retry loop.

## Phase 54: EditSystemSheet Reconciler Integration (Phase 19d)

Closes the "Not sure → confirm later" loop teased at the end of Phase 19c. When the user edits a home system's subtype or category via `EditSystemSheet` (e.g. HVAC "not_sure" → "boiler_radiant", or Water Heater nil → "tank"), the existing orphan-confirmation dialog was removing inappropriate template tasks correctly, but it wasn't adding any of the templates that became newly applicable under the new subtype. Users upgrading from Not Sure to a real type saw the same task list and wondered whether the app had actually done anything. Phase 19d adds the missing "add" half while keeping the orphan dialog's keep/delete choices authoritative.

**New `ReconcileMode` enum on `MaintenanceTaskReconciler`.** Three values: `.full` (the existing behavior — add newly-applicable templates AND soft-delete orphans), `.addOnly` (only insert templates that became newly applicable, never delete), and `.removeOnly` (only soft-delete orphans, never add — included for symmetry). The new `mode: ReconcileMode = .full` parameter on `reconcile(propertyId:householdId:systemId:systemCategory:confirmedSubtype:fuelType:flags:mode:)` defaults to `.full` so every existing caller (`HouseQuizAnswerMapper`'s eight per-question reconcile sites, `HouseQuizViewModel.runFinalReconciliation`, `AppState.reconcileAllPropertiesOnce`, and the two internal `reconcileAll` loops) keeps working unchanged. The implementation gates the template-insert block on `mode != .removeOnly` and the task-archive block on `mode != .addOnly`.

**`EditSystemSheet.commitSave` wires the reconciler in.** After `db.updateHomeSystem` returns the new row and after any orphan deletions from the confirmation dialog complete, the sheet runs:
```swift
await MaintenanceTaskReconciler.reconcile(
    propertyId: updated.propertyId,
    householdId: updated.householdId,
    systemId: updated.id,
    systemCategory: updated.category,
    confirmedSubtype: updated.subtype,
    fuelType: updated.catalogFuelType,
    mode: .addOnly
)
```
Gated on `updated.subtype != system.subtype || updated.category != system.category` so no-op saves (user changed only a note or manufacturer) skip the reconcile entirely. `.addOnly` mode guarantees the reconciler never touches existing tasks, so the user's explicit "Keep tasks" choice from the orphan dialog is preserved — the cooling tune-up they said keep still gets kept, and "Bleed radiators" / "Annual boiler service" land alongside it.

**Confirmation toast.** `@State var addedTaskCount` on `EditSystemSheet` drives a bottom overlay that renders a small cream card with a green checkmark and "Added N new maintenance task(s)" copy, styled the same as Phase 19's "Your place is saved." toast. The sheet delays dismissal by ~1.2 seconds (`Task.sleep(nanoseconds: 1_200_000_000)`) when `addedCount > 0` so the toast is actually visible, then dismisses normally. When nothing was added the dismissal is instant. The toast posts `.maintenanceTaskChanged` so the parent `SystemDetailView` / `MaintenanceScheduleView` refresh their task lists once the sheet goes away.

## Phase 54E.2: Biweekly / monthly cadences + vendor linking

Follow-on to Phase 54E. The initial cadence model assumed every rhythm repeats weekly (days-of-week only) and had no vendor link, which broke down the moment Tom tried to add his cleaning lady (every 2 weeks) and his lawn crew (monthly). This sub-phase extends the schema, iOS model, edit sheet, row rendering, and push-notification edge function to support biweekly / tri-weekly / every-4-weeks (~monthly) frequencies AND optional contractor linking so vendor-backed cadences pull in the contractor's logo and name.

**Schema:** New migration `20260604_household_cadence_vendor_frequency.sql` drops the `cadence_type_valid` CHECK constraint (unknown iOS enum values now fall back to `.other` gracefully, so adding future types doesn't need a migration) and adds three columns to `household_cadences`: `weeks_interval int not null default 1 check (weeks_interval between 1 and 12)`, `anchor_date date` (nullable), `contractor_id uuid references contractors(id) on delete set null`. Existing rows default to weekly/null anchor/null contractor so their current behavior is preserved.

**New cadence types:** `cleaning`, `lawn_care`, `pool_service`, `pest_control` added to the `HouseholdCadenceType` enum in `Haven/Features/Property/Models/HouseholdCadence.swift` alongside the existing waste/school/delivery types. **Frequency math:** `HouseholdCadenceRow.isActive(on:calendar:)` is the new shared predicate — checks weekday membership first, then (when `weeksInterval > 1`) computes `weeks = daysSinceAnchor / 7` and matches only when `weeks % weeksInterval == 0` AND candidate >= anchor. Dates before the anchor never match. Missing `anchor_date` falls back to `created_at` so a misconfigured row still renders a sensible rhythm. `isActiveToday` / `isActiveTomorrow` now delegate to this predicate, which transparently upgrades the `PickupDayBanner` surfacing math without touching its call sites.

**Expander:** `CadenceOccurrenceExpander` gained a private `matchesFrequency()` helper that runs the same weeks-since-anchor math for every cursor day. `parsedAnchorDate()` decodes the Postgres `date` string as start-of-day in the calendar's timezone, so DST edges don't drift the week count.

**Edit sheet:** `CadenceEditSheetEntry` gained three controls:
- A "Repeats" Menu picker with "Every week" / "Every 2 weeks" / "Every 3 weeks" / "Every 4 weeks" mapping to `weeksInterval` 1-4. No custom interval field — the four-option ladder covers the real-world set (cleaning, lawn, pool) and keeps the UI compact.
- An anchor-date `DatePicker("Next occurrence")` that appears only when `weeksInterval > 1`. Explanatory footer: "We'll use this date as the reference week. For a cleaner every other Wednesday, pick the next Wednesday she's coming."
- A "Service provider (optional)" section with a tappable row that opens the existing `ContractorPickerSheet`. ## Phase 54E.4: Comprehensive duplicate cleanup + uniqueness guards

Tom reported "Pet Waste Removal" and "Snow Removal" appearing twice in the contractor directory's "Assign Systems" picker and asked me to sweep the whole database for similar duplicates. Root cause: multiple code paths that seed home_systems (quiz completion + AppState backfill + legacy universal seed) all ran their own fetch-then-insert dedup check, which races when two run concurrently on the same property. The fix ships five SQL migrations: three data-cleanup passes + two defensive unique indexes that prevent future recurrences.

**Scan + fix scope:** I audited every table where multi-path creation could produce duplicates and ran dedup where duplicates were found:

| Table | Result |
|---|---|
| `home_systems` | **4 duplicates dropped** on Tom's household: Handyman, Mosquito & Tick, Pet Waste Removal, Snow Removal — one each. |
| `maintenance_tasks` | **4 duplicates dropped**: Appliance:Deep clean dryer vent duct, Garage Door:annual, Generator:annual, Septic System:triennial (template-keyed, likely reconciler races). |
| `contractors` | 0 duplicates found — the existing Phase 19k name-dedup held. Defensive index added anyway. |
| `utility_accounts` | **1 duplicate dropped**: Blue Fox Landscaping (same property, same provider type, same name). |

**FK-safe deletion pattern:** Every dedup pass rewires all FK references from the losing rows to the canonical keeper BEFORE the DELETE runs. Without the rewire the `ON DELETE CASCADE` on the child tables would silently drop the user's maintenance history. Coverage per pass:
- `home_systems` dedup rewires: `home_systems.parent_system_id`, `maintenance_tasks.system_id`, `service_records.system_id`, `warranties.system_id`, `standing_appointments.system_id` (guarded by information_schema for older installs).
- `contractors` dedup rewires: `maintenance_tasks.assigned_contractor_id`, `home_systems.preferred_contractor_id`, `service_records.contractor_id`, and optionally `household_cadences.contractor_id`, `service_contracts.vendor_id`, `project_contacts.contractor_id`, `standing_appointments.vendor_id`.

**Canonical selection:** For each duplicate group, the migration picks the row with the most user-enriched metadata (preferred contractor link > service history > manufacturer/model details > brand identity) and falls back to the oldest `created_at` as tiebreak. Before DELETE, COALESCE null-fills the keeper from any loser that had better data — so information doesn't vanish just because the scoring picked a different row for a different reason.

**Unique partial indexes to prevent recurrence:**
- `uniq_home_systems_property_name_subtype` on `(property_id, LOWER(TRIM(name)), LOWER(COALESCE(subtype, '')))` WHERE `parent_system_id IS NULL`. Keeps sub-systems unconstrained (multiple "Pool Pump" rows under different parents are legitimate) and lets wood-vs-gas chimney coexist via the subtype key.
- `uniq_maintenance_tasks_property_template` on `(property_id, template_id)` WHERE `template_id IS NOT NULL AND is_archived = false`. Lets archived-then-regenerated tasks coexist while blocking two active rows with the same template.
- `uniq_contractors_household_name` on `(household_id, LOWER(TRIM(company_name)))`. Every iOS insert path already wraps in `try?`, so collisions surface as no-ops rather than crashes.
- `uniq_utility_accounts_property_type_name` on `(property_id, provider_type, LOWER(TRIM(provider_name)))`. Provider type is in the key so Redding Sanitation stays as separate rows under trash + recycling (user's real-world pattern).

**Files created:** `supabase/migrations/20260605_dedup_home_systems.sql`, `supabase/migrations/20260606_home_systems_uniqueness_guard.sql`, `supabase/migrations/20260607_dedup_maintenance_tasks.sql`, `supabase/migrations/20260608_maintenance_tasks_uniqueness_guard.sql`, `supabase/migrations/20260609_dedup_contractors.sql`, `supabase/migrations/20260610_dedup_utility_accounts.sql`. **Files modified:** `PROGRESS.md`.

## Phase 55.1: Routines unification — data migration (no UI changes yet)

First of three halt points in Phase 55. **The conceptual model:** Everything that recurs is a Routine. Everything that requires per-instance coordination is a Task. Trash day (cadence), Renata's biweekly cleaning (standing appointment), and Blue Fox lawn care (standing appointment) are all Routines — they just happen on a schedule, the user doesn't book each visit. Annual roof inspection, septic pumping, and snow-plow contract renewal are Tasks — they require phone-picking-up on every instance. The two previous tables conflated those concepts; `routines` is the unified primitive.

**Schema (`20260700_routines.sql`):** New `routines` table with identity (`label`, `routine_kind`, `icon`, `notes`), vendor + system FKs, cadence (`cadence_type`, `cadence_interval_days`, `days_of_week`, `time_of_day`), schedule anchors (`start_date`, `next_expected_date`, `last_confirmed_date`, `last_assumed_date`), active-months array (default year-round), reminder flags, optional cost in cents, pause/archive lifecycle, and migration-provenance columns (`migrated_from_cadence_id`, `migrated_from_standing_appointment_id`, `cadence_source`, `confidence_score`). `routine_kind` CHECK covers service-based kinds (cleaning / landscaping / pool_service / pest_control / pet_waste / mosquito_tick / snow_removal / gutter_cleaning / window_cleaning / tree_service / handyman_recurring) and cadence-based kinds (trash / recycling / compost / yard_waste / recurring_delivery / school_dropoff / school_pickup) plus two catch-alls. `cadence_type` CHECK covers weekly/biweekly/triweekly/monthly/bimonthly/quarterly/semiannual/annual/custom_days. Four invariant CHECKs guard active_months (non-empty, in 1-12 range), custom_days (requires interval), and weekly variants (require days_of_week — the expander's keying constraint). Five indexes for the common query shapes. Paired `routine_visits` table mirrors `standing_appointment_visits` shape with routine_id FK, status, confirmation metadata, and actual_cost_cents. RLS scoped via `get_my_household_id()`; service_role gets full access for cron.

**Backfill (`20260701_routines_backfill.sql`):** Idempotent via ON CONFLICT targeting partial unique indexes on the `migrated_from_*` columns. Three passes:
- Cadences → routines: maps 54D types through their identity kind, 54E.2 service cadences (cleaning / lawn_care / pool_service / pest_control) to their matching routine_kind (lawn_care → landscaping), 54E.2 `weeks_interval` to the corresponding routines cadence_type (1/2/3 → weekly/biweekly/triweekly, 4+ → custom_days with interval = weeks*7), 54E.2 `contractor_id` to `vendor_id`, and 54E.2 `anchor_date` to `start_date`. Service-based cadences pull `seasonal_pause_months` from `category_cadence_defaults` so Blue Fox landscaping routines land with `active_months = {4,5,6,7,8,9,10,11}` automatically; non-service cadences default to year-round.
- Standing appointments → routines: maps `home_systems.category` to routine_kind via a LOWER/CASE ladder, composes label from vendor name + service description with fallback to system name/category, preserves cadence + pause state + provenance. Standing appointments don't carry `days_of_week` natively (they're anchored on `start_date` with an interval), so weekly/biweekly/triweekly rows synthesize `days_of_week = [EXTRACT(DOW FROM start_date) + 1]` to satisfy the routines CHECK constraint. Active-months pulls from category_cadence_defaults via the same LOWER(REPLACE(category, ' ', '_')) lookup.
- Standing appointment visits → routine_visits: straight join via `migrated_from_standing_appointment_id`, preserves the original visit id so any iOS code holding onto the legacy UUID still resolves.
- `maintenance_tasks.routine_id` added as nullable new column (old `standing_appointment_id` preserved for rollback); UPDATE repoints every task where `routine_id IS NULL` and a matching routine exists.

**Verification block:** Hard assertions that rollback the migration on mismatch. Captured counts for Tom's household: cadences 1→1, appointments 7→7, visits 29→29, tasks with appointment 4→4 (0 orphaned). Spot-checked three rows of each kind — Trash cadence landed as routine_kind `trash` year-round; Blue Fox Landscaping appointment landed as routine_kind `landscaping` biweekly April-November with vendor_id linked; Renata's Cleaning Services appointment landed as routine_kind `cleaning` biweekly year-round with vendor linked.
